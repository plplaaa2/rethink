# LG RAC_056905_WW 프로토콜 문서

## 범위와 증거 기준

이 문서는 LG ThinQ 2 기반 벽걸이 에어컨 처리기 `RAC_056905_WW`의 TLV 통신, 제어값, 센서 환산식과 현재 구현의 안전 제약을 정리한다.

주요 근거는 다음 파일이다.

- `cloud/devices/RAC_056905_WW.ts`: 실제 프로토콜 처리기
- `cloud/devices/tlv_device.ts`, `util/tlv.ts`: 프레임과 TLV 인코딩
- `tests/cloud/devices/RAC_056905_WW.test.ts`: 실제 캡처 및 회귀 테스트
- `docs/rac-tlv-sensor-investigation.md`: 운전 상태별 센서 관측 기록
- `util/ac_tables.ts`: RAC 온도 환산표

증거 수준은 다음처럼 구분한다.

- **확정**: 실제 명령/상태 왕복 또는 반복 관측과 테스트로 확인됨
- **강한 후보**: 운전 변화와 일관되게 연동되지만 공식 정의나 독립 검증이 부족함
- **미확인**: 원시값만 관측됐거나 의미를 확정할 근거가 부족함

이 문서는 공식 LG 사양서가 아니라 역공학 기록이다. 다른 RAC 모델에 동일한 기능 비트나 열거값을 그대로 적용하지 않는다.

> 경고: 임의 TLV 쓰기는 예기치 않은 기동이나 장치 상태 변경을 일으킬 수 있다. 특히 전원이 꺼진 상태에서 Jet cool 값 `1`을 쓰면 냉방으로 즉시 기동할 수 있다. 검증된 조합만 사용하고 실제 장치 시험은 사람이 현장 상태를 확인할 수 있을 때 수행한다.

## 전송 프레임

### 서버에서 장치로 보내는 TLV 프레임

```text
a s 04 00 00 00 65 byte6 byte7 byte8 tlv_length tlv... crc16_be
```

현재 처리기가 사용하는 헤더 조합은 다음과 같다.

| 용도           | 앞의 두 바이트 | `byte6 byte7 byte8` | TLV                   |
| -------------- | -------------- | ------------------- | --------------------- |
| 기능 조회      | `01 01`        | `02 02 01`          | `0x1F5=1`             |
| 전체 상태 조회 | `01 01`        | `02 02 01`          | `0x1F5=2`             |
| 설정 쓰기      | `01 01`        | `02 01 01`          | 변경 필드와 연관 필드 |

CRC16은 앞의 `a s`를 제외한 `04`부터 TLV 끝까지 계산하며 결과를 big-endian 두 바이트로 붙인다.

실제 기능 조회 패킷:

```text
01010400000065020201027D416A0D
```

여기서 TLV `7D41`은 `0x1F5=1`이다.

### 장치에서 서버로 오는 TLV 프레임

처리기가 수용하는 일반 응답/알림의 핵심 형태는 다음과 같다.

```text
.. 04 00 00 00 87 02 type sequence tlv_length tlv... crc16_be
```

- `type`: 현재 구현은 `0x01` 또는 `0x04`를 수용한다.
- `sequence`: 알림/응답 순번이다.
- `tlv_length`: 뒤따르는 TLV 바이트 길이다.
- 수신 CRC는 Wi-Fi 모듈이 이미 검증한다고 가정해 처리기에서 다시 검사하지 않는다.

기능 응답은 `0x2DA` EEPROM checksum TLV 포함 여부로 식별한다. 전체 상태 응답은 TLV가 10개 이상이고 `0x1F7` 전원 TLV를 포함하는지로 식별한다.

## TLV 인코딩

각 TLV는 최소 2바이트다.

```text
byte0 = tag[9:2]
byte1[7:6] = tag[1:0]
byte1[5:4] = 추가 value 바이트 수(0~3)
byte1[3:0] = 추가 바이트가 없을 때 4비트 value
```

value는 필요한 최소 길이로 인코딩한다.

| 값 범위        | 길이 필드 | 전체 TLV 크기 | 값 저장 방식              |
| -------------- | --------: | ------------: | ------------------------- |
| `0x00~0x0F`    |         0 |       2바이트 | 두 번째 바이트 하위 4비트 |
| `0x10~0xFF`    |         1 |       3바이트 | 뒤의 1바이트              |
| `0x100~0xFFFF` |         2 |       4바이트 | big-endian 2바이트        |
| 그 이상        |         3 |       5바이트 | big-endian 3바이트        |

예시:

```text
7D C0       = tag 0x1F7, value 0
7E 44       = tag 0x1F9, value 4
7F 50 29    = tag 0x1FD, value 41
C8 41       = tag 0x321, value 1
```

## 초기화와 갱신 흐름

1. 연결 직후 `0x1F5=1` 기능 조회를 보낸다.
2. `0x2DA`가 포함된 기능 응답을 받으면 `0x1F5=2` 전체 상태를 조회한다.
3. 초기 전체 상태를 받은 뒤 TLV blacklist를 비워 변경 알림을 모두 요청한다.
4. 지원 장치에서는 별도 private 명령으로 필터 데이터를 조회한다.
5. 기본 전체 상태 갱신 주기는 15분이다.
6. 냉방·제습·난방처럼 값이 빠르게 변하는 운전 중에는 약 28초로 단축한다.
7. 활성 운전이 끝난 뒤 15분이 지나면 기본 주기로 돌아간다.

모든 TLV 변경이 비동기 알림으로 오는 것은 아니므로 주기 조회를 완전히 제거하면 안 된다.

## 기본 운전 제어

### 핵심 TLV

| TLV     | 기능           | 원시값/변환             | 쓰기 시 함께 보내는 필드      | 증거 |
| ------- | -------------- | ----------------------- | ----------------------------- | ---- |
| `0x1F7` | 전원           | `0=OFF`, 그 외 `ON`     | ON: `0x1F9`, `0x1FA`, `0x1FE` | 확정 |
| `0x1F9` | 운전 모드      | 아래 모드 표            | `0x1FA`, `0x1FE`              | 확정 |
| `0x1FA` | 팬 단계        | 아래 팬 표              | `0x1F9`, `0x1FE`              | 확정 |
| `0x1FD` | 현재 실내 온도 | `raw / 2` °C, 읽기 전용 | —                             | 확정 |
| `0x1FE` | 설정 온도      | `raw / 2` °C            | `0x1F9`, `0x1FA`              | 확정 |

설정 온도 상태는 0.5°C 단위로 해석하지만 현재 장치 제어는 정수 °C만 지원하므로 쓰기값을 반올림한 뒤 `×2`한다. Home Assistant 노출 범위는 현재 `18~30°C`이며 기능 TLV에서 동적으로 얻은 범위는 아니다.

기능 응답의 `0x2C1`은 허용 운전 모드, `0x2C2`는 온도 범위 후보지만 현재 해석하지 않는다. 일부 장치는 `0x2E1~0x2EC`로 모드별 온도 범위를 보고하는 것으로 보이나 이 처리기에는 아직 매핑이 없다.

### 운전 모드 `0x1F9`

| raw | 모드   | Home Assistant |
| --: | ------ | -------------- |
|   0 | 냉방   | `cool`         |
|   1 | 제습   | `dry`          |
|   2 | 송풍   | `fan_only`     |
|   3 | 미정의 | 노출하지 않음  |
|   4 | 난방   | `heat`         |
|   5 | 미정의 | 노출하지 않음  |
|   6 | 자동   | `auto`         |

전원이 꺼져 있으면 모드 TLV 값과 관계없이 `off`로 표시한다. `off` 명령은 모드값을 쓰지 않고 `0x1F7=0`을 보낸다.

### 팬 단계 `0x1FA`

| raw | 단계      |   안정 상태 관측 RPM |
| --: | --------- | -------------------: |
|   2 | Very low  |   목표 850, 실제 840 |
|   3 | Low       |   목표 920, 실제 930 |
|   4 | Medium    |     안정 측정 미완료 |
|   5 | High      | 목표 1100, 실제 1090 |
|   6 | Very high | 목표 1200, 실제 1190 |
|   8 | Auto      |     부하에 따라 가변 |

목표 RPM `0x2FB`와 실제 RPM `0x331`은 모두 `raw × 10 rpm`으로 해석된다. 현재 Home Assistant에는 실제 RPM `0x331`만 노출한다.

### climate action

실제 운전 여부는 장치가 제공하는 태그 중 `0x189`를 우선 사용하고, 없으면 `0x06C`를 사용한다.

- 전원 OFF: `off`
- 냉방/제습/난방/자동이지만 IDU running이 0: `idle`
- 냉방: `cooling`
- 제습: `drying`
- 송풍: `fan`
- 난방: `heating`
- 자동 운전 중: 실제 하위 모드를 확정할 수 없어 action을 비운다.

## 풍향 제어

### 세로 풍향 `0x321`

`0x321`은 세로 회전, 고정 날개 각도, 간접 바람이 공유한다. 읽기 필드는 하나만 등록하고 세 Home Assistant 상태를 파생 발행해야 한다.

| raw | 의미                             |
| --: | -------------------------------- |
|   0 | 세로 회전 OFF                    |
| 1~6 | 고정 날개 위치                   |
|   1 | 간접 바람 ON으로도 해석          |
|   6 | 현재 구현의 간접 바람 OFF 명령값 |
| 100 | 세로 회전 ON                     |

간접 바람 스위치는 `ON→1`, `OFF→6`을 쓴다. 따라서 고정 위치 1은 간접 바람 ON으로 표시되며 위치 6은 OFF로 표시된다. 이 공유 관계를 분리된 독립 TLV처럼 취급하면 상태가 서로 덮어써질 수 있다.

실제 캡처:

```text
간접 바람 ON 쓰기  0101040000006502010102C8416527
간접 바람 OFF 쓰기 0101040000006502010102C84615C0
```

### 가로 풍향 `0x322`

| raw | 의미          |
| --: | ------------- |
|   0 | OFF           |
| 1~5 | 고정 위치 1~5 |
|  13 | 위치 범위 1~3 |
|  35 | 위치 범위 3~5 |
| 100 | 회전 ON       |

## 부가 제어

| TLV     | 기능               | 값/변환                          | 동작 제약                    | 증거           |
| ------- | ------------------ | -------------------------------- | ---------------------------- | -------------- |
| `0x20D` | Energy saving      | `0=OFF`, `1=ON`                  | 실제 보고 상태를 그대로 표시 | 확정           |
| `0x20E` | Auto dry           | `0=OFF`, `1=ON`                  | 실제 보고 상태를 그대로 표시 | 확정           |
| `0x20F` | Air purify         | `0=OFF`, `1=ON`                  | 전원이 켜졌을 때만 쓰기      | 구현/관측 기반 |
| `0x21A` | Sleep timer        | raw 분, HA 시간=`ceil(raw/15)/4` | 0~15시간, 0.25시간 단계      | 구현됨         |
| `0x21B` | Turn-off timer     | raw 분, 동일 변환                | 0~24시간                     | 구현됨         |
| `0x21C` | Turn-on timer      | raw 분, 동일 변환                | 0~24시간                     | 구현됨         |
| `0x225` | Auto dry remaining | raw %, 읽기 전용                 | —                            | 구현됨         |
| `0x323` | Jet cool/heat      | `0=OFF`, `1=Cool`, `2=Heat`      | 아래 설명 참조               | 확정           |

Jet ON은 전원이 이미 켜져 있고 현재 모드가 냉방이면 `1`, 난방이면 `2`를 쓴다. 다른 모드 또는 전원 OFF에서는 ON 명령을 보내지 않는다. OFF 값 `0`은 모드와 관계없이 쓸 수 있다. 장치가 보고한 raw가 지원되는 `1` 또는 `2`이면 현재 모드와 관계없이 스위치를 ON으로 표시한다.

Auto dry 실제 캡처:

```text
ON 쓰기   010104000000650201010283816D5D
OFF 쓰기  010104000000650201010283807D7C
ON 상태   000004000000870204FE0283817DA9
OFF 상태  0000040000008702045502838099E1
```

`0x21F` Display light 후보는 모델에 따라 값의 극성이 다르고 ThinQ 앱에도 표시되지 않아 현재 노출하지 않는다.

## 센서 TLV

아래 표의 **코드 구현**은 처리기에 변환·등록 로직이 있다는 뜻이고, **HA 노출**은 Home Assistant Discovery 엔티티가 실제 생성되는지를 뜻한다. `조건부` 엔티티는 초기 상태에 해당 TLV와 유효값이 있을 때만 생성된다.

| TLV                  | 현재 명칭                | 변환/단위                   | 코드 구현 | HA 노출           | 노출 조건·비고                                   | 증거      |
| -------------------- | ------------------------ | --------------------------- | --------- | ----------------- | ------------------------------------------------ | --------- |
| `0x221`              | Error code               | raw                         | 예        | 조건부, 진단 센서 | 태그가 있을 때 생성                              | 구현 확인 |
| `0x228`              | Compressor frequency     | raw Hz                      | 예        | 조건부, 일반 센서 | 태그가 있을 때 생성                              | 확정 수준 |
| `0x232`              | Current operation energy | `raw / 1000` kWh            | 예        | 조건부, 일반 센서 | 태그가 있으면 Total energy도 함께 생성           | 확정 수준 |
| 소프트웨어 파생      | Total energy             | `0x232` 변화량 누적, kWh    | 예        | 조건부, 일반 센서 | `0x232`가 있을 때 생성, 장치 원시 TLV는 아님     | 구현 확인 |
| `0x2B3`              | Power                    | `max(5, raw - 60)` W        | 예        | 조건부, 일반 센서 | 초기 raw가 0이 아니면 생성                       | 비교 확인 |
| `0x2F9`              | Pipe liquid temperature  | `racPipeTemp[255-raw]` °C   | 예        | 조건부, 진단 센서 | raw 0/1이면 미지원 sentinel로 보고 생성하지 않음 | 구현 확인 |
| `0x2FA`              | Pipe gas temperature     | 동일                        | 예        | 조건부, 진단 센서 | raw 0/1이면 생성하지 않음                        | 구현 확인 |
| `0x32B`              | ODU suction temperature  | 동일                        | 예        | 조건부, 일반 센서 | raw 0/1이면 생성하지 않음                        | 강한 후보 |
| `0x07A` 또는 `0x32C` | ODU HEX temperature      | 동일                        | 예        | 조건부, 일반 센서 | 존재하는 첫 번째 태그를 사용                     | 구현 확인 |
| `0x32E`              | Capacity nominal         | `round(raw×0.293×10)/10` kW | 예        | 조건부, 진단 센서 | raw 0이면 생성하지 않음                          | 구현 확인 |
| `0x330`              | EEV opening              | raw                         | 예        | 조건부, 일반 센서 | 일부 IDU/ODU 조합에서 값 신뢰성 문제             | 구현 확인 |
| `0x331`              | Fan RPM                  | `raw × 10` rpm              | 예        | 조건부, 일반 센서 | 실제 IDU 팬 속도                                 | 확정      |
| `0x332`              | ODU air temperature      | `racAirTemp[255-raw]` °C    | 예        | 조건부, 일반 센서 | 전용 환산표 사용                                 | 구현 확인 |

### 온도 환산

배관 계열은 `racPipeTemp[255 - raw]`, ODU 공기 온도는 `racAirTemp[255 - raw]` lookup table을 사용한다. 두 표의 index 255는 불연속적인 `-100°C`에 해당해 sentinel로 비워 두었다.

`0x2F9`, `0x2FA`, `0x32B`의 raw 0과 1은 일부 장치가 미지원 센서에 보내는 값이므로 실제 극저온으로 발행하지 않는다.

### 보정된 현재 소비전력

`0x2B3`은 raw를 그대로 W로 표시하지 않고 `max(5, raw - 60)`으로 보정한다. `RAC_056905_WW`에서 스마트플러그와 비교한 결과 운전 구간의 변화 추세와 측정 크기가 대체로 일치해 현재 소비전력 센서로 정상 동작하는 것이 확인됐다.

다만 다음 특성은 남아 있다.

- 약 50~60 W의 양의 편향이 있다.
- 대기 구간은 최소 5 W 처리와 장치 보고 특성 때문에 스마트플러그보다 낮을 수 있다.
- 상태 갱신 간격 때문에 급격한 상승·하강 구간은 계단 형태와 짧은 시차가 생긴다.
- 다른 RAC/IDU/ODU 조합에서는 동일한 정확도를 보장하지 않는다.

따라서 이 모델에서는 **스마트플러그 비교로 확인된 보정 소비전력**으로 설명하되, 계량기급 원시 W 값이나 정산용 측정값으로 취급하지 않는다.

### 장기 Total energy

`Total energy`는 장치가 직접 제공하는 TLV가 아니다. `0x232` 회차 누적 Wh의 변화량을 소프트웨어가 합산한다.

- 새 값이 이전 값 이상이면 차이만 더한다.
- 새 값이 감소하면 새 운전 회차가 시작된 것으로 보고 새 값을 더한다.
- 최초 관측값은 전체 누적값의 시작점에 포함한다.
- 총 Wh와 마지막 회차 Wh를 장치별 영구 상태로 저장한다.
- 센서는 매 패킷 갱신하지만 디스크 저장은 최대 30초에 한 번과 정상 종료 시 수행한다.

영구 상태를 삭제하면 소프트웨어 누적 기준도 사라진다.

## 필터 private 프로토콜

필터 정보는 일반 TLV가 아니라 private 명령 `0x02` 계열을 사용한다.

### 조회

```text
command = 0x02
subcommand = 0x02
```

응답 데이터는 첫 바이트 뒤에 little-endian uint32 세 개를 담는다.

| 위치    | 값                        | 코드 구현 | HA 노출           |
| ------- | ------------------------- | --------- | ----------------- |
| `1..4`  | Filter used time, h       | 예        | 조건부, 진단 센서 |
| `5..8`  | Filter life time, h       | 예        | 조건부, 진단 센서 |
| `9..12` | 마지막 교체일, `YYYYMMDD` | 예        | 조건부, 진단 센서 |

필터 private 조회가 성공하고 lifetime이 0보다 클 때 위 센서와 `Filter dirty`, `Reset filter usage` 엔티티를 생성한다. `Filter dirty`는 장치 원시값이 아니라 `min(100, used/lifetime×100)`을 소수점 한 자리로 반올림한 진단 센서이며, 초기화는 진단 버튼으로 노출된다.

### 초기화

초기화 전에 최신 필터 데이터를 다시 조회한다. 이후 `command=0x02`, `subcommand=0x01`로 보내며 payload의 lifetime과 날짜는 조회 응답과 달리 big-endian uint32로 인코딩한다. 초기화 응답이 성공이면 다시 조회해 상태를 갱신한다.

필터 조회가 EEPROM 쓰기를 유발할 가능성이 있어 주기 갱신은 하루 한 번으로 제한한다.

## 기능은 알려졌지만 현재 미노출된 TLV

수신된 TLV는 공통 parser의 raw state에는 저장되지만, 아래 항목은 Home Assistant 필드나 엔티티로 등록하지 않는다.

| TLV              | 후보 의미            | 값 해석 구현 | HA 센서 노출 | 현재 판단                                              |
| ---------------- | -------------------- | ------------ | ------------ | ------------------------------------------------------ |
| `0x2FB`          | Target fan RPM       | 문서화만     | 아니요       | `raw×10 rpm` 확정, 실용성이 낮아 의도적으로 미노출     |
| `0x22A`, `0x32F` | 미확인 ODU 운전값    | 아니요       | 아니요       | 서로 같은 값이며 운전 중 최대 15, 정지 시 0으로 관측됨 |
| `0x229`          | ODU/압축기 연동값    | 아니요       | 아니요       | 의미 미확인                                            |
| `0x233`          | 제어값 또는 카운터   | 아니요       | 아니요       | 의미 미확인                                            |
| `0x2FD`, `0x2FE` | 빠르게 변하는 내부값 | 아니요       | 아니요       | 팬 단계/목표 RPM은 아님                                |
| `0x21F`          | Display light        | 아니요       | 아니요       | 모델별 극성 불일치                                     |

세부 운전별 원시값과 시간 상관관계는 `docs/rac-tlv-sensor-investigation.md`에 유지한다.

실제 압축기 주파수로 구현된 태그는 `0x228`이다. `0x22A/0x32F`는 과거 압축기 주파수 후보였지만 `0x228`의 실제 운전 범위가 확인된 뒤 그 해석을 폐기했다. 현재는 ODU 운전 여부와 연동되는 값이라는 사실만 확인됐으며 단위와 의미는 미확인이다.

## 안전한 추가 검증 항목

1. Medium 팬을 30초 이상 유지해 `0x2FB`와 `0x331`의 안정 RPM을 기록한다.
2. 전원 종료·재부팅·자정 전후에 `0x232` 초기화 경계를 확인한다.
3. 별도 전력계와 `0x2B3`을 냉방·난방·송풍별로 비교해 보정식을 검증한다.
4. 물리 표시등을 안전하게 전환할 수 있는 모델에서 `0x21F` 극성을 확인한다.
5. `0x229`, `0x233`, `0x2FD`, `0x2FE`를 압축기 부하와 시간축으로 비교한다.
6. 다른 IDU/ODU 조합에서 `0x330` EEV 값의 소유 장치를 확인한다.

검증되지 않은 TLV는 먼저 읽기 전용으로 수집하고, 의미가 확정되기 전에는 Home Assistant 제어나 자동화에 사용하지 않는다.
